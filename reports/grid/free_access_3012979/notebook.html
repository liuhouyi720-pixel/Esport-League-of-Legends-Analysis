What can my current GRID access do?¶

Example: Worlds 2026 semifinal, Gen.G vs Invictus Gaming, November 7 (GRID series 3012979). This was a BO5 that finished 3–0: there are three played games, not five observations.

This notebook uses a real, richer Series State response retrieved with your working Open Access key. It does not call the File Download API. The previous file-download rejection applies to that product/series; it does not establish a universal rule about free versus commercial accounts.

We first inspect schema, row grain and completeness, then explore bans/picks (BP), final gold differences, player summaries and objective totals. An optional final section draws a sparse gold-difference line using Oracle's Elixir checkpoints, clearly separated from GRID data.

How to run: select the project .venv kernel and Run All. The default reads cached real data and makes no API calls, so a blank key is expected. To request a fresh snapshot, set REFRESH_FROM_API = True below. A completed-series snapshot does not contain a historical gold or movement trace.

4. Audit completeness before gameplay summaries¶

The grain audit checks keys, rosters, game results, same-game team joins, five picks/five bans per team, and agreement between drafted champion IDs and player champions. Blocking failures stop downstream EDA. Reconciliation differences are reported separately for review and never silently corrected.

5. Ban/pick statistics and draft order¶

Join draft actions to teams using (game_id, team_id), then keep only champion picks and bans. BP presence counts distinct games in which a champion was picked or banned, divided by the number of fully audited games. The denominator is three games, not six team-game rows or the BO5 maximum of five. A count of zero below means an action type was absent from these audited complete drafts; it does not replace missing raw data.

Champion availability can depend on the tournament's draft rules and earlier games. Without a separately verified availability model, this is observed selection frequency, not an availability-adjusted preference.

7. Basic player and objective review¶

Summarize kills, deaths, assists, gold and vision at player-series grain using stable player IDs. Rates below divide series totals by the sum of the three game durations; this avoids giving a short game equal weight to a long game. KDA uses the ratio of series totals. A zero death denominator stays undefined.

These summaries describe output and resource distribution. They do not identify tactical errors or causal player impact. The team/player kill discrepancy remains in the audit, so we avoid deriving kill participation. Roles are unavailable in this snapshot and generic damageDealt is not treated as champion damage.

Objective types overlap: slayDragon includes elemental dragon types. The selected table uses only generic dragon, Baron and tower totals. An omitted objective type stays missing (NaN), not an assumed zero.

8. Optional gold-difference line: a separate Oracle's Elixir source¶

This section does not use GRID gold history. The existing local Oracle CSV provides selected gold checkpoints at 10, 15, 20 and 25 minutes. We select the three explicitly referenced Riot/Oracle game IDs, use team rows only, validate both teams and the November semifinal date window, and keep the sign Gen.G − IG. Game numbers and roster champions must agree before the cross-source comparison is accepted.

Checkpoints are eligible only if the game lasted beyond that minute, both sides report values, and the opposite-side differences reconcile. Missing points stay missing. Lines connect observed points as a reading aid; they do not reconstruct intervening gold, turning points or continuous telemetry. GRID final gold is not appended to this other publisher's curve.

Oracle and GRID can disagree on duration or final totals because their definitions or cutoff times differ. The comparison table reports discrepancies without claiming their cause. Turn off INCLUDE_ORACLE_CHECKPOINTS for a GRID-only run.

9. Save the results and decide what to explore next¶

Export the full audit and tidy tables so you can inspect all records beyond the previews. These outputs contain match data and provenance, never credentials. The notebook also retains all rendered charts.

Useful next projects with this access are a larger BP sample, pick order by team/side, champion-pool diversity, gold and vision summaries, and objective control summaries after checking coverage in each new series. Expand with Central Data discovery and one state query per selected series, caching each result; do not assume that coverage here extends to every competition.

A future gold-over-time chart could come from live snapshots you collect while an accessible series is actually running, if your account allows live state. Save each response with retrieval time, game ID and game clock, verify that the source state advances, and deduplicate unchanged updates. This has polling resolution, not event resolution, and cannot recover earlier history. GRID currently documents Open Access limits of six state requests per minute per series; check your account limits before designing a collector. This notebook does not start a polling loop.
